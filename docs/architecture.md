# SpaceSentinel — Architecture

## Overview

SpaceSentinel is a simulation and proof-of-concept prototype. It does not
control real spacecraft. All telemetry is synthetically generated by the
backend simulation engine.

```
┌─────────────┐      HTTP (REST, polling)      ┌──────────────────────┐
│   Frontend   │ ───────────────────────────── │       Backend         │
│ React + Vite │                                 │   FastAPI (Python)    │
│  TypeScript  │ ◀───────────────────────────── │                        │
└─────────────┘                                 └──────────┬───────────┘
                                                             │
                                                     ┌───────▼────────┐
                                                     │  SQLite (logs,  │
                                                     │  anomaly hist.) │
                                                     └─────────────────┘
```

## Backend pipeline

```
TelemetryEngine (engine.py)
        │  generates 1 sample/sec, scenario-driven drift + noise
        ▼
AnomalyDetector (anomaly.py)
        │  Layer 1: hard safety thresholds
        │  Layer 2: trend-sensitive statistical z-score
        │  Layer 3: IsolationForest vs. fixed nominal baseline
        ▼
AppState.reconcile_anomalies (main.py)
        │  tracks active anomalies per metric, persistence count,
        │  resolves anomalies once metric returns to normal
        ▼
score_risk (risk.py)               generate_predictions (prediction.py)
        │  0-100 transparent score          │  linear trend + time-to-threshold
        ▼                                    ▼
generate_insights (ai_analysis.py)
        │  rule-based explainable NLG, NOT an LLM call
        ▼
REST API (main.py) ── polled by the React frontend every 1.5-3s
```

## Modules

| File | Responsibility |
|---|---|
| `backend/app/models.py` | Pydantic schemas for every domain object |
| `backend/app/engine.py` | Telemetry simulation: nominal setpoints, noise, per-scenario drift |
| `backend/app/anomaly.py` | Hybrid 3-layer anomaly detection |
| `backend/app/risk.py` | Deterministic mission risk scoring (0-100) |
| `backend/app/prediction.py` | Linear-regression trend + threshold-crossing estimate |
| `backend/app/ai_analysis.py` | Rule-based explainable insight generation |
| `backend/app/database.py` | SQLite persistence for mission logs + resolved anomaly history |
| `backend/app/main.py` | FastAPI app, background simulation loop, REST endpoints |
| `frontend/src/lib/api.ts` | Typed REST client |
| `frontend/src/hooks/usePoll.ts` | Generic polling hook for live data |
| `frontend/src/pages/*` | One page per application area (Overview, Spacecraft, Telemetry, Anomalies, AI Analysis, Predictions, Simulation, Mission Logs, Settings) |

## Data flow / freshness

The backend runs a 1Hz background loop (`_simulation_loop` in `main.py`)
that only advances state while a simulation is running. The frontend polls
REST endpoints on independent intervals (1.5-3s depending on the page) via
`usePoll`. There is no WebSocket in this MVP — REST polling was chosen for
simplicity and reliability within the competition timeline; a WebSocket
push model is a natural v2 improvement (see `docs/development-workflow.md`).

## Why REST polling instead of WebSockets (MVP decision)

Given the "simplest reliable option" priority in the project brief, REST
polling was chosen over WebSockets/SSE for the MVP: it is trivial to test
with `curl`, has no reconnect/backpressure logic to build, and at 1-3
requests/second per client the overhead is negligible for a demo. WebSocket
streaming remains a documented future improvement.
